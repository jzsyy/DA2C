# DA2C Experimental Settings

[English](experiments.md) | [简体中文](experiments.zh-CN.md) | [Project overview](../README.md)

This document describes the reported experimental protocol. The implementation, executable configurations, and reproduction scripts are planned for release upon paper acceptance.

## Evaluation protocol

- Backbones: Qwen3-8B and Qwen3.8-27B, with frozen model weights and separately calibrated routers.
- Evaluation: 13 tasks and 3,975 questions, comprising six BBH tasks (250 each), GSM8K (1,319), and six MMLU tasks (144, 173, 145, 237, 223, and 234).
- Seeds: 42, 43, and 44. Tables report three-run means; corrected and harmed counts are rounded to integers after averaging.
- Main-table overall accuracy is the equally weighted mean across 13 tasks. Ablation, routing, and budget accuracy pools all questions within each run, then averages across runs.
- Online token usage includes input/output tokens for initial generation, checking, interventions, selection, review, and retries. Offline router calibration and graph optimization are recorded separately from online usage.

## Router calibration

The development protocol samples 200 GSM8K training questions and 200 MMLU validation questions, removes test overlap by question fingerprints, and partitions by question into 60% fitting, 20% selection, and 20% independent checking. Action branches reuse the same candidate and diagnostic state, with two repeats per action. Each action has a gain model and a log-cost model. Later states are generated by seeded random available actions without reference-answer-based selection.

The 34-dimensional feature vector describes answer relations, format and confidence validity, diagnostic categories, cognitive operations, check sources and verdicts, the round, and the remaining budget. Per-action standardization uses the fitting partition. Categorical confidence labels remain categorical. The code release will include the exact encoder and stored feature order with the router artifacts.

## Baselines

| Method | Configuration |
| --- | --- |
| CoT | One sample |
| Self-Consistency | Three candidates and answer voting |
| Best-of-N | Three candidates; a same-backbone selector whose calls count toward online cost |
| BloomWise-BLES | Actual online early stopping when valid adjacent-level answers agree; final-level answer otherwise |
| BloomWise-BLM | Aggregation across all six levels |
| MAD-M2 | Subjective masking, three agents, two rounds including initialization |
| AgentPrune | Authors' public graph optimization, pruning, and regularization implementation; development-optimized general graph transferred to BBH; mathematical graph uses GSM8K training data |
| MAPS (text-adapted) | Personality-based collaboration and feedback, with visual inputs removed |
| GPT-5.4 Direct / Reasoning | Separate closed-source capability references |

CoT, Self-Consistency, and Best-of-N use temperature 0.2, top-p = 1, up to 2,048 output tokens per call, and no calculator. AgentPrune mathematical roles retain code execution. MAD-M2, BloomWise, and AgentPrune do not share DA2C's 8,000-token total scheduling target. The main comparison reports each method's operating point and actual online usage.

## Controlled ablations

Variants share frozen initial candidates for each question and seed and are each charged full initial-generation cost. Each re-collects action outcomes and refits its router on the same development partitions while keeping the full method's alpha/lambda.

| Variant | Change |
| --- | --- |
| Generic question chain | Retain claim targeting; remove cognitive categories and operation descriptions |
| Fixed cognitive order | Preset Remember-to-Create order; up to three questions with normal early stopping |
| Shuffled question chain | Seed-permute operation order; generate each question from the current state |
| w/o Bloom labels | Neutral category IDs with functional descriptions and adaptive selection retained |
| w/o claim-level diagnosis | Reconsider the first candidate matching the current answer in fixed order; remove pre-checking and verify_step; retain evidence rechecking, whole-solution repair, arbitration, and review |
| w/o diagnostic checking | Mark check features missing; retain arithmetic screening and acceptance review |
| w/o acceptance gate | Directly commit format-valid proposals not blocked by arithmetic screening |
| w/o re-diagnosis | Reuse the initial diagnostic/check record; stop on missing targets or repeated actions |

Missing diagnostic/check features use explicit missing encodings consistently during calibration and evaluation. Removing diagnostic checking retains diagnosis and target localization; removing acceptance review retains diagnostic checks and arithmetic screening.
